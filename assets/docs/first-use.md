# TauLoop：给 Codex 的第一次介绍

这是一份给 Codex 看的首轮说明。用户第一次问 TauLoop 怎么用时，用自然语言介绍，不要先列命令、目录或内部术语。

## 用一句话介绍

TauLoop 帮你把一个项目目标拆成清楚的小任务，让 Codex 一项项完成、验证并留下进度。这样工作换会话也不会丢，而且长任务不会靠反复查看日志来假装推进。

## 第一次对话怎么说

先告诉用户三件事：

1. 用户只需要说想达成什么，例如“推进到 v1”或“把环境配好”。
2. 我会把目标拆成 specs。每份 spec 都会写清做什么、怎么确认完成。
3. 每完成一份，我会验证并写 checkpoint；遇到需要用户决定、权限或费用、验证失败时才停下来。

然后只问一个有用的问题：**“你希望我先推进什么目标？”**

## 这些词怎么解释

- **任务**：用户想得到的结果。
- **Spec**：任务的一张小工作卡，说明范围和完成标准。
- **Checkpoint**：完成一段工作后留下的事实记录；下一次可以从这里继续。
- **Harness**：项目里保存计划、结果和问题的共享记录。
- **长任务**：需要等待的串行工作，例如下载、安装、训练或测试。

不要一次讲完这些词。用户问到哪个，就用一句话解释哪个。

## 有目标后怎么做

- 始终用 /.codex 中的 plan、memory等来维护“项目级”记忆
- 根目录的 `AGENTS.md` 说明每次工作从哪里开始；`.codex/plan.md` 记录当前推进内容，`.codex/memory.md` 保存仍然重要的事实。
- 目标明确后，创建或更新一份父任务和必要的 specs。
- 用户说“先给我看计划”时，只展示计划和完成标准，等待确认。
- 用户说“持续推进”时，依次完成可执行的 specs；每份都验证、写 checkpoint，再开始下一份。
- 用户指定 `spec1` 到 `spec4` 时，只推进这些 spec，不扩展到无关工作。

## 长任务怎么做

当任务包含下载、安装、训练或一串有顺序的命令时，先写出执行计划和每一步的验证方法。监督真实进程，低频记录健康证据；前一步没有通过验证，就不能开始下一步。

不要把 heartbeat、仍在运行的进程或很长的日志说成“完成”。不要频繁轮询下载进度。

## 应该停下来的情况

在下面情况停下来，请用户决定：

- 新的权限、费用或不可逆修改。
- 验证失败、依赖缺失，或恢复需要选择。
- 用户要求 review，或目标已完成并需要验收。

TauLoop 是前台本地工具。它不会在终端关闭或电脑重启后继续，也不会因为测试样例通过就保证 CUDA、GPU 或仿真器真的可用。
