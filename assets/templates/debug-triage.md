# Debug Triage — 排障先查证

**适用场景**：常规开发任务中遇到 bug / 错误 / 失败 / 行为异常。**无人值守长任务巡检请用 `shift-agent.md`**——两者共享"先调研再修"的纪律，本模板只覆盖有上下文的主 agent 场景。

**核心原则**：先查证，后修复。修复必须基于证据与根因，不允许盲修（试运气改法、绕开现象、改验收标准凑通过）。查证不到不是修复的借口——是交班的理由。

---

## 一、触发（缺一不可判断，满足即可进入流程）

- 测试失败 / 命令报错 / 日志出现异常 / 行为与预期不符。
- 用户报告 bug（即使你认为"一眼就能修"）。

**可跳过的例外（仅限这些，且跳过要在 spec 排障段写明）**：
- 纯格式/拼写/机械替换，无行为变化；
- 无网络环境（查证不可行）——写明"未查证"与残余风险。

## 二、五步流程（按顺序执行）

### 第 1 步 复现与取证

- 记下**可复现的最小步骤**：命令、输入、环境（版本/平台/依赖）。
- 收集原始证据：错误信息原文、栈、日志尾部、最小复现样例。**证据要能贴进 spec，不是"报错了"三个字。**

### 第 2 步 写根因假设

- 一句话写出你怀疑的根因，且**可证伪**（"如果假设对，那么 X 应该发生"）。
- 写不出可证伪的假设 = 还没到修复阶段。

### 第 3 步 查证（本模板的核心）

按优先级查证，**每条记录来源**（链接 / issue # / commit / 章节 / 论文标题）：

1. **官方文档**：当前版本、对应平台。快、权威、覆盖大多数问题。
2. **上游仓库**：源码 + issue tracker。用**错误信息原文片段**搜 GitHub（选最独特的 3–8 个词，不要整段贴）；查相关 issue 的状态（open/closed/fixed in which version）。
3. **开源社区**：Stack Overflow、相关论坛、同类项目。注意区分"看起来像"与"同版本同场景"。
4. **论文 / arXiv / 官方技术报告**：**科研向提前到第 2 位**。触发信号（满足其一）：仓库是研究项目（如 `.harness/brief.md` 标注）、bug 落在算法/方法实现层、owner 声明科研场景。用现有文献调研能力检索，并顺带查**论文附带代码仓库**的对应 issue。

查证目标不是"找到答案"，是**验证或推翻你的根因假设**。查到的资料若与假设矛盾，改假设，不要硬凑。

### 第 4 步 最小修复 + 回归验证

- 只改最小范围，修复前先备份或记录原值。
- 跑最窄的验证（单测 / 单命令 / 最小样例），**验证不过 = 修复无效 = 回到第 2 步**，不许带病继续。
- 禁止：push、发布、删除数据、改动测试或验收标准来"通过"。

### 第 5 步 证据落盘

把第 1–4 步压缩写进 spec 的「排障证据」段（或 plan 的当前任务段）：

- **现象**：错误原文 / 复现命令
- **查证记录**：看过什么（来源列表），得到什么结论
- **根因结论**：最终假设 + 为什么
- **修复依据**：为什么这样修（引用查证到的来源或推理）
- **残余风险**：没查到的、没验证到的

可复用的失败模式（同类问题会再犯的）→ 追加进 `.harness/failure-log.md`。

## 三、硬性纪律

1. **先查证后修复**：没有查证记录就动手修 = 盲修。修复类任务默认要能说出"哪里查的、为什么这样修"。
2. **假设先行**：没有可证伪的根因假设，不进入修复。
3. **不绕开现象**：屏蔽报错、catch 后吞掉、改验收标准——都不算修。
4. **不盲目重试**：同一招连续 2 次无效，必须换思路（换查证路径或交班），不许原地打转。
5. **诚实**：查不到就写"查不到"，绝不编造来源或结论。查证耗尽仍无解 = 交班（写清：观察到 / 试过 / 调研过 / 建议下一步）。
6. **证据可复核**：来源要具体（URL、issue #、commit、章节），不写"网上说"。
